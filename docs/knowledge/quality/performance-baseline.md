# 性能基线(启动 / 大文档 / 输入 / 包体)

> 分类:质量基线。数字全部来自 CI 实测,改动后对照这里看有没有退化。PRD 质量要求:冷启动 ≤1 秒、5MB 文档首屏 ≤1.5 秒、输入 p95 ≤16 毫秒、安装包 ≤30MB。

## 从哪里取数
- 真应用:macOS CI 的冒烟(`ci/smoke-macos.sh` → `ci/macos` 分支 `smoke/smoke.json`),在 WKWebView 里打开 5MB 文档、连续输入、保存。
- 规模曲线:`perf` 工作流(推到 `perf` 分支触发,`editor/scripts/perf-profile.mjs`),Chromium 跑 256KB~5MB、Playwright WebKit 跑 64KB~5MB(07f508b 那次 WebKit 只测到 512KB:预览服务的子进程占着日志管道,剖析步骤挂到超时,6d39720 已修),报告在 `ci/perf` 分支 `perf/perf.md`。另有启动剖析(到编辑器就绪的 CPU 剖析与按模块的脚本覆盖率,201f81e 起)。
- 本机实机冒烟只作参考:窗口被遮挡或用户在操作时,WebKit 会节流定时器与 requestAnimationFrame(2026-10-16 本机 4 次 5MB 首屏从 286 毫秒到 93 秒不等),数字以 CI 为准。

- **输入延迟还剩什么**(冒烟细分,b140e46):每键约 9 毫秒里「视图 DOM 更新」约 5.9 毫秒,其中真正改动的那一块自己的更新只占约 0.07 毫秒;照补丁写法把 54678 个顶层块逐个比对一遍约 5.3 毫秒(WebKit 里每块约 100 纳秒)。再往下压要让快速路径不再逐个比对全部顶层块(例如按改动位置只看附近、用旧文档定位改动范围),三种读法分别计时(e44afaf / 701bf76,各 30 次全量比对,含闭包调用开销):只比节点对象与脏标记 84 / 42 毫秒,再读装饰数组长度 185 / 90 毫秒,再算节点大小 228 / 136 毫秒——读装饰数组(多碰一个对象)让耗时翻倍,算节点大小再加三到五成。可做的方向:装饰按引用比(与共享的空数组比,不读长度)、扫描范围里没有装饰时不算节点大小、只在改动位置附近比对。这三项诊断计时分析完已从冒烟去掉(每轮多跑 90 次全量比对、不做断言),要复查时从 e44afaf 的 `editor/src/smoke.ts` 取回。
- **启动对比(同一台机器、同一次运行,perf 工作流 76f34ae)**:`editor/scripts/startup-ab.mjs` 把拆包前最后一个提交(7f63a3b)与当前代码各构建一份生产包,轮流冷启动 11 轮(新浏览器上下文、无缓存),量导航到编辑器就绪。Chromium 中位 201 → 166 毫秒(−17%),WebKit 中位 423 → 376 毫秒(−11%),两边各次不重叠;启动时下载的脚本 1478KB → 929KB(gzip 478 → 291KB)。为什么要同机:同一份代码换一台 CI 机器,冷启动中位能从 258 变成 163 毫秒,跨运行的数字不能直接比。复跑:`git push -f origin HEAD:perf`,结果在 `ci/perf` 分支 `perf/startup-ab.md`。
- 输入延迟怎么降下来的:冒烟按阶段拆分每键耗时(`timings` 里的 `input · …`),大头在 ProseMirror 视图逐个比对 5 万个顶层块(每键约 15 毫秒),其次是 prosemirror-tables 的修表格逐个比对(约 3 毫秒)。两处都靠依赖补丁跳过前后没变的部分(见 `decisions/large-document.md` 第 4 条)。p95 变化:基础版 44(3a84a91)→ 19(3843c14)→ 16(34f34a7)→ 16(cbd4644)→ 11(808cb0e)→ 12(5b7b820)→ 18(b140e46)→ 15(e44afaf)→ 12(a5bc8cb);AI 版 47 → 20 → 17 → 13 → 15 → 17 → 16 → 17 → 11 → 14 → 14。剩下的每键约 6 毫秒已查明在逐个比对顶层块(见「输入延迟还剩什么」)。
- 本机实测方法:下载 CI 的 DMG 挂载后把 .app 复制到临时目录(不装进「应用程序」),先备份 `~/Library/Application Support/Typoza/settings.json`,连续跑 `Typoza.app/Contents/MacOS/Typoza --startup-check-out <目录>`(就绪后约 4 秒自动退出,报告里有 `readySeconds` 与 `launchMarks`),跑完核对设置未变。稳态 0.52 秒时各段:原生启动到建好 WebView 约 0.16 秒,建好到开始导航约 0.17 秒,导航到就绪约 0.19 秒。

## 补充实测(2026-10-22~23,公开仓库后的 CI)

- 规模曲线(perf,3970137):Chromium 全文载完 1 / 2 / 5MB = 1.3 / 2.5 / 6.5 秒;Linux WebKit 1 / 2 / 5MB = 2.1 / 3.8 / 11.4 秒,都近似线性。
- 启动剖析(Chromium,到编辑器就绪 566 毫秒):启动时加载却没执行的大头是 @codemirror/view 256KB、katex 189KB(示例文档含公式才加载)、yaml 164KB(不压缩构建的字节数)。按需加载 CodeMirror / yaml 是下一步可做的启动优化。
- macOS CI 冒烟抖动很大:同一份代码 readySeconds 从 1.93 到 3.99 秒、5MB 全文载完 6.3~13.7 秒、输入 p95 17~54 毫秒;慢的那几次连原生启动(willFinishLaunching)都从 0.04 秒变成 0.39 秒,是排队后的虚拟机本身慢。比较前后改动要看同一轮或多轮的趋势,不看单次。
- 启动时间点(冒烟 launchMarks):didFinishLaunching 结束 → 网页进程开始导航约 0.6 秒;导航结束 → 编辑器就绪约 0.4~0.5 秒(其中应用初始化约 0.3 秒)。
- AI 版:冒烟全部检查通过,数字与基础版同量级(同样受虚拟机抖动)。

## 已知的大头
- 解析:5MB 里 micromark 占 3.8 秒(真应用),已靠分段变成线性,再快只能换解析器(见 `decisions/large-document.md`)。
- 启动:`webViewCreated` → `navigationStarted` 之间是网页进程启动,外壳侧能做的只有尽早建 WebView、尽早发起导航。
