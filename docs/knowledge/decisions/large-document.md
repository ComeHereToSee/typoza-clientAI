# 决策:大文档(MB 级)怎么做到首屏快、输入不卡

> 分类:决策(ADR)。2026-10-16。PRD 质量要求:5MB 首屏 ≤1.5 秒、输入 p95 ≤16 毫秒。

- **背景**:ProseMirror 要求整篇文档在状态里、整篇 DOM 渲染;micromark 解析慢;每次按键要重排整篇。
- **选项**:换解析器(markdown-it 等,要重写整条转换管线与扩展语法)/ 节点视图做真虚拟化(侵入所有块类型)/ 分段解析 + 渐进打开 + 视口裁剪(都只动边缘)。
- **结论**:第三种。
  1. 分段解析:只在「分开解析与整篇解析结果相同」的块边界切(不切在围栏代码、公式、HTML 块、`<details>` 里,不切在列表项前;有链接 / 脚注定义时不切),块的原文索引与间隔跨段接续,未编辑的块仍逐字写回。单测比对分段与整篇结果完全相同。
  2. 渐进打开:先显示第一段,其余每步 50ms 预算内解析、一次追加;载完前只读、不能保存 / 导出 / 切源码(正文不全,防止把半截写回)。
  3. 视口裁剪:顶层块 ≥1500 时离视口远的块用样式表(`:nth-child` 规则,挂在外层容器类上)隐藏、容器内边距补高度;试过节点装饰,几万块时 `DecorationSet` 平方级卡死,已退回(见 `pitfalls/webkit-editing.md` 第 2 条)。
  4. 视图快速更新(2026-10-23 补):ProseMirror 每次更新都逐个比对容器的全部子节点(preMatch 建 Map、iterDeco 逐个算装饰),5 万个顶层块时 WebKit 里每键约 15 毫秒。`scripts/patch-deps.mjs` 给 prosemirror-view 打补丁:子节点 > 200 的块级容器先走快速路径——前后没变的子节点只比节点对象、脏标记与装饰标记,中间只改了一个子节点时原地 update;容器层有小部件或行内装饰、增删子节点、输入法组合不在这个子节点里、原地更新不了都退回原逻辑。单测逐步对照「同一状态新建的视图」的 DOM;冒烟核对打的字画到了界面上。
- **理由**:改动集中在 `core/markdown/chunks.ts`、`parse.ts` 的 `MarkdownChunks`、`app.ts` 的 `continueLoading`、`plugins/viewport.ts`,其余功能不感知;小文档行为完全不变。
- **代价**:载入中不能编辑;视口外的块高度先估后量,快速滚动可能短暂露白;超过 10MB 仍以只读源码打开。
- **实测**(CI,07f508b):真应用 5MB 首屏 297 毫秒、全文载完 6.3 秒(改前 19 秒)、输入 p95 17 毫秒;Chromium 全文载完 1MB 1.7 秒 / 2MB 4.7 秒 / 5MB 7.3 秒,近似线性。
